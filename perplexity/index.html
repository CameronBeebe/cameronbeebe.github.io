Perplexity, cross-entropy, and bits per byte

Perplexity is not a mysterious leaderboard number. It is the exponential of average log loss — the strictly proper scoring rule that rewards an honest probability — written as an effective branching factor. It is also not a fair way to compare language models that cut text into different tokens. Bits per byte is.

This page is a v0 explainer. Measured token probabilities below were computed on a CPU with publicly released checkpoints, on short passages, and are labeled as such. They are not full WikiText or C4 benchmark runs. A toy byte-level trigram, trained on WikiText-2 raw train, scores any text you type.

One loss, four unit systems

A causal language model assigns a probability \(p(x_t \mid x_{<t})\) to each next token. The logarithmic score of the token that actually arrived is \(\log p\). Average that, change the sign, and you have the usual training objective: cross-entropy, also called log loss or negative log-likelihood.

\[ \mathrm{CE}_{\text{nats}} = -\frac{1}{N}\sum_{t=1}^{N}\log p(x_t\mid x_{<t}), \quad \mathrm{PPL} = e^{\mathrm{CE}_{\text{nats}}} = 2^{\mathrm{CE}_{\text{bits}}}, \quad \mathrm{CE}_{\text{bits}} = \frac{\mathrm{CE}_{\text{nats}}}{\ln 2}. \]

Perplexity is that average surprise, turned back into a count: the size of a uniform distribution that would have the same entropy. A perplexity of 8 means the model is as uncertain, on average, as if it were choosing among 8 equally likely tokens. Bits per token is the same quantity in base 2 — the expected code length if you compressed the tokens with the model’s probabilities.

Bits per byte (BPB) keeps the total surprise in the numerator and changes only the denominator, from “how many of this model’s tokens” to “how many UTF-8 bytes in the text”:

\[ \mathrm{BPB} = \frac{\sum_t (-\log p(x_t\mid x_{<t}))}{(\ln 2)\, B} = \left(\frac{N}{B}\right)\mathrm{CE}_{\text{bits}}. \]

Two models can be compared in BPB even when their tokenizers disagree, because they are being asked how many bits they needed to describe the same bytes. Raw token-level perplexity cannot do that: a tokenizer that makes more, shorter tokens creates more, easier prediction steps, and its perplexity looks better for bookkeeping reasons. The Pile paper adopted BPB for this invariance; Paloma uses it whenever vocabularies must differ. OpenAI’s GPT-2 paper already made the same move in spirit, reporting perplexity per canonical dataset unit (a word, a byte, a character) rather than per BPE token.

Effective branching factor

Move the slider to feel the units change together. Nothing here is a trained model: a uniform distribution over \(k\) options has perplexity \(k\), and each prediction costs \(\log_2 k\) bits.

Log loss is a strictly proper scoring rule

A scoring rule grades a probabilistic forecast against the event that happened. It is strictly proper when the unique way to optimize your expected score is to report the probabilities you actually believe. The logarithmic score \(S(p,y)=\log p(y)\) is strictly proper; so is the Brier score, which is a squared error. Language-model training minimizes expected log loss, which is why a well-trained model is rewarded for being calibrated, not merely for being peaked.

Suppose you believe the next bit is 1 with probability \(q\), and you are allowed to report any \(p\). Your expected log loss under that belief is uniquely minimized at \(p=q\). Reporting a sharper or softer number cannot help you, and it can hurt you.

Why raw perplexity misleads across tokenizers

Hold the joint surprise of a text fixed and only change the unit you divide by. Perplexity moves; bits per byte does not. That is the bookkeeping artifact, isolated from any difference in how well two models actually fit the text. The joint used here is real: it comes from the toy byte trigram on this page, scoring the text in the box below (or any text you type in the playground).

What published numbers already exist

Credible, comparable perplexity tables for today’s small open models are thinner than the number of blog posts suggests. Official model cards for Llama, Gemma, Qwen, Phi, and SmolLM2 typically report downstream accuracy, not WikiText or C4 perplexity. Community figures often differ in context length, stride, dataset version (WikiText-2 vs WikiText-103, raw vs tokenized), and whether the reported perplexity is per BPE token or per word. The tables below cite a source and a protocol, and they are not a single leaderboard.

GPT-2 paper, zero-shot, per canonical dataset unit

What I am not treating as a leaderboard

  • The official Llama 2 paper does not report WikiText-2 perplexity. Figures around 5.5–5.8 for Llama-2-7B appear in later compression and quantization papers, under varying context lengths, and should not be quoted as an official Meta number.
  • Official Qwen, Gemma, and Phi model cards I checked emphasize downstream benchmarks, not a standard WikiText or C4 perplexity table.
  • Paloma (Magnusson et al., 2023) is the right framework for domain-level fit and for BPB when vocabularies differ. Its public baselines are controlled 1B models trained for the paper, not a ready-made ≤8B Qwen/Llama/Gemma leaderboard. Dataset: paloma.allen.ai (redirects to the Hugging Face card, HTTP 200).

What this demo adds

Interactive token visualizations already exist. perplexity.vercel.app and MPN’s Perplexity visualizer run GPT-2 in the browser and color tokens by surprise; Prism does the same for confidence; PicoGPT-JS trains a 64-symbol character model in the page. Written explainers — mbrenndoerfer, Long Form Explainers, LeetML, and the Fix the Robot lab — cover the algebra, and several warn that perplexity is tokenizer-dependent.

What they generally do not do, together, is treat perplexity as a proper scoring rule, keep bits per byte on screen next to token-level perplexity, and show a measured two-tokenizer comparison (GPT-2 BPE vs SmolLM2) on the same passages. That is the gap this page is for: an eval-flavored portfolio piece, not another single-model heatmap.

How the numbers on this page were computed

On 23 November 2026, America/Denver, a CPU box ran compute_scores.py with PyTorch 2.15.0+cpu and Transformers 5.24.0. Checkpoints: gpt2 (124,439,808 parameters, vocab 50,257), distilgpt2 (81,912,576, same tokenizer), and HuggingFaceTB/SmolLM2-135M (134,515,008, vocab 49,152). Each text was encoded with add_special_tokens=False — none of these tokenizers prepends BOS — and scored in one float32 forward pass. The first token is shown but not scored, because it has no context. Bits per byte uses only the UTF-8 bytes of the concatenated scored tokens in the denominator. The scripts are in scripts/.

The toy model is a byte-level interpolated trigram (weights 0.4 / 0.4 / 0.2 on trigram, bigram, and add-1 unigram over a 256-byte alphabet) trained on the Salesforce WikiText-2 raw train split (10,914,845 bytes). Trigrams with count < 3 and bigrams with count < 2 are treated as unseen. The first two bytes of a string are not scored. It is a demonstration model, not a competitor to GPT-2.
